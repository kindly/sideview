# v0 — markdown and HTML blocks, done well

The other documents describe where this could go. This one describes what to build, and
everything absent from this page is deliberately absent.

**The whole of v0:** an agent appends prose and HTML blocks to a page that is already open in
your browser, and they appear as they are written.

That is worth building even if nothing else ever follows, because it beats the current
HTML-artifact flow on the two things that actually hurt — the agent writes a fraction as much,
and you see the first block in a second instead of the whole document in a minute.

## In

- **CLI**: `sideview prose` / `markup` / `html` taking content on stdin, `sideview show <file>`,
  plus `update <id>` and `rm <id>` — the whole of what an agent ever uses. For you: bare
  `sideview`, and `sessions`, `status`, `styles`, `reset`. Nothing else.
- **Store**: SQLite, blocks as rows.
- **Daemon**: serves the page, notices new blocks, patches the open page over SSE. Auto-starts,
  long-lived, never parented to a tty.
- **Browser**: opens on first use, and *only* on first use.
- **Four block types**: `prose` (markdown), `markup` (inline, inherits the page's styles),
  `html` (sandboxed iframe, whole document), `image`.
- **The design system** — the class vocabulary, typography, light and dark. Not decoration:
  this is the product.
- **The skill** — without it the agent never reaches for any of the above.

## The CLI surface

Two audiences with different entry points — not two disjoint sets, which an earlier draft claimed
and which isn't true. **Agents** only ever use the six authoring subcommands: `prose`, `markup`,
`html`, `show`, `update`, `rm`. **You** type bare `sideview`, plus a few inspection subcommands an
agent has no reason to call — except `styles`, which is for the agent and useful to you when
writing the skill.

```bash
$ sideview            # ensure the project's daemon is up, then open the page
$ sideview sessions   # what's running here, and at which URLs
$ sideview status     # is the daemon alive, on which port, at which version
$ sideview styles     # print the class vocabulary
$ sideview reset      # delete the store and start again (pre-1.0 escape hatch)
```

Bare `sideview` takes `--detach` and `--bind auto|loopback` (default `auto`, which includes the
tailnet address when there is one); the remote section covers the second.

That is the entire surface. Note what is deliberately absent: there is no `sideview start` and no
`sideview daemon` subcommand. Bare `sideview` starts one if needed, and stopping it is Ctrl-C in
the terminal that owns it — see the version-skew note below, where an earlier draft's
`sideview daemon --restart` turned out to be incoherent with foreground ownership.

Bare `sideview` is idempotent: if a daemon is already running *and reachable* it just opens the tab
and exits, rather than starting a second. (Reachable is doing real work in that sentence — see
"Detecting whether a daemon can be reached at all" below.) If it starts one, it runs in the foreground with its log, and
Ctrl-C stops it. `--detach` if you'd rather. It deliberately does *not* print help with no
arguments — a tool that does the useful thing beats one that lectures you, and help lives at
`--help`.

Every authoring subcommand prints the id it created, on stdout, alone. (There is no `add`
subcommand — that spelling is left over from DESIGN.md's `sideview block add prose`, and the
verb-first form here replaced it.) The printed id is the entire mechanism by which an agent learns
a block's identity, and everything else depends on it:

```bash
$ sideview prose <<'EOF'
The current parser drops blank unit rows.
EOF
b7
$ sideview update b7 <<'EOF'
The current parser drops blank unit rows — about 4% of the 2024 file.
EOF
$ sideview rm b7
```

**Ids are per-session counters, and `update`/`rm` resolve them within the caller's own session.**
`b7` is short because an agent has to pass it back through a shell, and short means a counter
rather than a uuid — which means two concurrent agents in one project both hold a `b7`. Resolving
against the resolved session makes that harmless and makes the wrong thing impossible to express:
an agent cannot name another session's block at all. The alternative — globally unique ids — was
rejected only because it makes the common case uglier for no gain, and this is exactly the
collision the `session_id` column exists to prevent.

Append-only was wrong. Plans are revised constantly — a paragraph gets fixed, a diagram
replaced — and without `update` the agent's only recourse is appending a correction below the
mistake, which reads badly and grows without bound.

`update` replaces a block's content in place, so the page patches that one block and nothing
scrolls or reflows around it. `rm` deletes it.

### `show` is the type-detecting front door

`show` exists to be the zero-thought ergonomic — point it at a file, get the file on screen,
no decision about block types. In v0 the only type it understands is images, because there is
no table or diff block yet, so `sideview show shot.png` is the whole of it today.

Keep the command anyway rather than shipping `sideview image`. The interface is then stable
while it quietly learns parquet, CSV and diffs later, and agents that learn `show` now keep
being right. Unsupported types get an honest error — *"don't know how to show .parquet yet"* —
not a silent failure.

**`show` copies a file in when it lives outside the project root.** The daemon only serves paths
inside the root, for the traversal reasons below — but the single most common image is a screenshot,
and agent screenshots land in `$TMPDIR` (`/tmp/claude-1000/…` here), which is outside it. Refusing
those would break the motivating case. So when the argument resolves outside the root, `show`
copies it to `.sideview/blobs/` and the block references the copy.

This does not weaken reference-never-embed, and the distinction is worth being precise about: the
rule is about what passes through *the model's context*, not about what the store touches. A 200KB
PNG copied by the CLI costs zero tokens; the same PNG base64'd into a spec costs a fortune. Copying
also fixes a real second problem — `$TMPDIR` is cleaned up, so a referenced screenshot would rot
while the page still pointed at it.

## One surface, not two

v0 has a **session page** and no concept of a named plan. Blocks append in order, which means
a plan is just a session page someone wrote in a sensible sequence and kept.

Naming, durability, promoting a scratch view into a document — all of that is a later layer
over the same rows, and none of it needs to exist for this to be useful.

## Out

Deferred, roughly in order of how much is being given up:

- **Service blocks** — supervising a live piece of the project. The most valuable long-term
  idea and much the most work. See the spike below.
- **`table` and `diff` blocks** — the showcase for reference-never-embed.
- **Provenance** — commit, working diff, input hashes, grades, `verify`.
- **Sharing** — snapshots, packing, tiers, Tailscale. *Except* that binding localhost on a
  stable port means `ssh -L` already works with no code at all. Don't build for remote; just
  don't break it.
- **The feedback channel** — comments and choices flowing back to the agent.
- **Params and interactivity**, plugin blocks, CSV backup, markdown export, Electron.
- **Syntax highlighting.** Plans are full of code and this matters for "done well", but the
  decision belongs with the `diff` block — the two want the same machinery, and choosing
  server-side (`syntect`) against client-side once, for both, beats choosing twice. Until then
  code blocks are styled but unhighlighted.
- **Mermaid and diagrams**, for the same reason: real demand, but not this version.

Markdown is rendered with **comrak** — GFM, so tables, task lists and strikethrough work, all of
which turn up constantly in plans and none of which CommonMark-only parsers handle.

## Do not cut these, even though they look cuttable

Each is nearly free now and genuinely expensive to retrofit:

1. **Blocks are rows with stable ids.** Identity cannot be added later without touching
   everything that ever referred to a block.
2. **A `session_id` column**, even with one surface. One column now; a collision nightmare
   later, the first time two agents share a project.
3. **A `version` field on the block spec, with a fallback rendering.** The Adaptive Cards
   lesson: renderers and content drift apart, and a block that degrades beats one that breaks.
   Concretely, and it needs to be concrete or it won't be implemented: a spec may carry
   `fallback` (a string of markdown), and a page meeting a `type` it doesn't know, or a `version`
   above what it renders, emits that string through the prose path inside a visibly marked
   container — *"this block needs a newer sideview"* — rather than an empty div or a thrown error.
   With four block types nothing exercises this yet, which is exactly why it is cheap today.
4. **Reference, never embed** — including here. An image block points at a path; it never
   inlines base64. The habit is the point, and it is the thing that makes later block types
   cheap.
5. **The startup path**: CLI returns immediately, race-free auto-start under parallel agents,
   one window rather than a tab per invocation, and a clear instruction rather than a hang when
   the daemon can't be reached. This *is* the feel of the tool, and the feel is what's being
   sold.

## The skill, modelled on hunk

A tool the agent doesn't reach for is worth nothing, and `--help` is not a mechanism — nothing
makes an agent read it unprompted. So the skill is a v0 deliverable, not documentation to write
afterwards.

Copy hunk's distribution model exactly: **the skill lives in the repo, and install symlinks it
into `~/.claude/skills/sideview`.** That's what hunkdiff does — `~/.claude/skills/hunk-review`
is a symlink into the npm package's own `skills/` directory — and the symlink is the point,
because the skill then updates with the binary and can never drift from the CLI's real flags.
(Worth noting the failure mode too: that particular link is currently broken because the
package moved. Uninstall should remove the link.)

What it has to carry, in roughly this order of importance:

1. **When to reach for sideview at all** — anything visual, anything too wide for a terminal, a
   plan or design argument, a screenshot. This is the part that actually changes behaviour.
2. **The six authoring subcommands**, and that each prints an id used by `update` and `rm`.
3. **Write semantic HTML; the page is already styled** — the single highest-leverage sentence
   in the whole skill, since it's what stops an agent hand-rolling four hundred lines.
4. **The `sv-` layer**, or a pointer to `sideview styles` rather than the list inline.
5. **What to do when the CLI says no daemon is running** — offer to re-run `sideview --detach`
   with the sandbox disabled, and relay the printed instruction if that's declined. This is the one
   place the skill carries operational instructions rather than authoring guidance, and without it
   the agent's only move is to print an error and continue as if nothing were wrong.

## The design system: borrow, don't invent

An earlier draft proposed inventing ~30 class names. That was wrong, because a vocabulary only
saves tokens if the agent already knows it, and a novel one has to be taught on every use. The
fix is to build almost entirely out of things models already have deep priors for. Three
layers, and only the third is invented:

**1. A classless base, for most of the page.** [Pico.css](https://picocss.com/) styles semantic
HTML directly — headings, paragraphs, tables, blockquotes, `<figure>`, `<details>`, `<kbd>` —
with fewer than ten classes in the whole framework, built-in light and dark themes following
the system preference, CSS-variable theming, one file, no JS and no build step.

The agent writes plain semantic HTML and it looks designed. Nothing to learn, nothing to
remember, nothing to print in a cheatsheet. And because markdown renders to exactly those
tags, **prose blocks and markup blocks style through the same path** — no separate prose CSS.

**2. Bootstrap-compatible names for components HTML has no element for.** `alert alert-warning`,
`card`, `badge`. Don't invent `sv-callout` when every model has seen `alert alert-danger` a
million times and will produce it correctly without being told. Borrow the *names*, not the
framework — Bootstrap itself is heavy and makes everything look like a Bootstrap site, whereas
a classless base reads like a clean document, which is what a plan should look like.

**3. A small domain layer**, prefixed `sv-`, for what genuinely has no precedent: the metric
and delta element for "3.2s → 0.4s" figures, option cards, a decision matrix. Six to ten
classes, which is the only part `sideview styles` needs to document.

Net effect: thirty invented names become fewer than ten, and the learning cost of the rest is
already paid.

**The risk this introduces, and the mitigation.** Borrowing Bootstrap names without Bootstrap
means a model may confidently emit `col-md-6` or `btn-primary`, which will silently do nothing
and quietly break a layout. So implement the common subset, and **log unknown `sv-`/Bootstrap
classes and inline `style=` attributes** the daemon renders. Silent no-ops become a measurement
of where the vocabulary falls short, and the input to the next round.

**That logging happens server-side, in the daemon, with a lenient HTML parser.** The obvious
alternative — spot them in the browser and POST them back — contradicts v0 having no browser→server
channel at all (see the SSE section), and would be the only thing forcing one into existence. The
daemon already has the markup in hand when it stores the block, so a pass over it there costs
nothing and needs no new endpoint.

**Which subset, decided against real plans and not in the abstract.** Both this list and the `sv-`
layer should be derived from three or four plans an agent actually wrote, because guessing at
`card`/`badge`/`alert` variants in advance is how design systems acquire members nobody uses. The
same note applies in HANDOFF.md to the `sv-` classes; it applies just as much to the borrowed ones.

### `markup` renders directly into the page, with no shadow root

DESIGN.md specifies a shadow root with `adoptedStyleSheets` for rung 2; this section said "inline,
inherits the page's styles". Those are not the same thing, and v0 takes the second: **render into the
document, no shadow boundary.**

The reason is that the shadow root's benefit is robustness against a block accidentally breaking the
page, and its cost is that Pico's element selectors — the entire mechanism by which semantic HTML
looks designed — stop reaching inside unless every sheet is explicitly adopted, on top of the sizing
and theming friction. Paying that in v0, where blocks come from an agent working on your own project
and the whole promise is *the page is already styled*, buys the wrong thing.

Revisit it when plugin blocks arrive, where the code genuinely isn't yours. Rung-1 `html` blocks are
already isolated in a sandboxed iframe, so the escape hatch for a block that must not touch the page
exists either way — and those iframes get the same base stylesheet injected, so isolated blocks look
consistent for free.

The code is modest — a Rust binary over `rusqlite` and `actix-web`, an SSE stream, a small
frontend. With the vocabulary mostly borrowed, the remaining design work is theming Pico's
variables and building the domain layer, which is a much smaller job than it was.

## Starting the daemon, and the one sandbox caveat

**Without a sandbox there is nothing to arrange.** The CLI spawns the daemon on first use, it
binds a port, the browser opens, and no service, unit file or manual step exists anywhere.
That is the baseline and it meets the aim in full. The one condition on it is the detection rule
two sections down: **auto-spawn unless this namespace is provably unreachable.**

**Sandboxed agents are the exception**, and the reason is specific. Measured on this machine:
each sandboxed Bash invocation gets its own **network namespace**. `bind()` and `listen()`
succeed inside it — the socket appears in `ss` within that same invocation, at a PID like 51,
which is itself the giveaway — but from the host there is no such port at all. So a daemon
spawned by a sandboxed agent isn't merely restricted, it is on a different network, and the
browser can never reach it. This is also the underlying reason hunk's localhost daemon and the
herdr socket have to be run with the sandbox off.

The mechanism is visible rather than inferred — the sandbox is `bwrap --unshare-net --unshare-pid
--unshare-user --cap-drop ALL --ro-bind / /` with the project directory and `$TMPDIR` bind-mounted
writable, which is also where "nothing under `$HOME`" comes from. And it has been checked in both
directions: a listener bound inside the namespace does not appear in the host's `ss` at all and the
host cannot connect to it, while the host's own loopback is unreachable from inside except through
the proxy described below.

**v0's answer: one daemon per project, started once by you.**

You run `sideview` in the project — outside the sandbox, because you are outside it. It binds a
port, opens the page, and stays. Every agent session in that project attaches to it, at its own
URL. Nothing is pre-allocated, nothing is claimed, and a session that starts at 3am attaches with
no setup at all.

The CLI then never prompts for anything, ever, because the one operation the sandbox actually
breaks — spawning a listener the browser can reach — has been lifted out of the agent's hands.
Everything the agent does is a write inside the project directory, which is already allowed.

An earlier draft had a *pool* of pre-started daemons that sessions claimed one apiece. It worked,
but all of its machinery — unclaimed state, LIFO ordering, stale reclaim — existed only to work
around the sandbox, and it made you decide **in advance** how many sessions you would run. Guess
low and you get the prompt you were avoiding. One daemon per project asks the question once, ever.

### Detecting whether a spawned daemon could be reached

The rule above needs a test, and the obvious candidate is wrong. **`$CLAUDECODE` is not it** —
measured on this machine, it is set to `1` both inside the sandbox and outside it, so keying on it
would refuse to auto-spawn in exactly the unsandboxed case the "Done when" bar requires. The same
goes for `$AI_AGENT` and `$CLAUDE_CODE_SESSION_ID`: they say an agent is present, not that the
network is namespaced.

Measured, same machine, one sandboxed Bash invocation against one with the sandbox disabled:

| signal | sandboxed | host |
|---|---|---|
| `/proc/self/ns/net` | `net:[4026532958]` | `net:[4026531833]` |
| `/proc/1/comm`, own pid | `bwrap`, pid 2 | `systemd`, pid 232035 |
| interfaces | `lo` | `lo eno1 wlan0 tailscale0` |
| routes | *(none)* | `default via 192.168.1.254` |
| `/proc/self/uid_map` | `1000 0 1` | `0 0 4294967295` |
| `$HTTP_PROXY` | set (`…@localhost:3128`) | unset |
| `$CLAUDECODE` | `1` | `1` |

**Don't detect the sandbox; detect the property.** The question is never "am I in a sandbox" — it is
"can a socket I bind here be reached from outside", and that is directly observable: *the namespace
has no non-loopback interface and no routes.* A daemon bound in there is unreachable by definition
rather than by inference, and `getifaddrs` (or reading `/proc/net/dev`) is a few lines with no
dependency worth arguing about. This also stays correct if the harness changes how it sandboxes,
because it tests the consequence rather than the cause.

**And the daemon records its own verdict**, as `netns` plus a `reachable` flag on its row, computed
once at startup. That is what closes the failure this section exists for.

#### The failure being closed

Worth stating plainly, because it is subtle and self-inflicted. A daemon spawned inside a sandbox
binds successfully, writes its row, polls `data_version`, and **answers ping/pong perfectly well** —
the store is not a network, so every liveness check in the next section passes. It is
indistinguishable from healthy to anything reading the store. Bare `sideview` then sees a
live daemon, "just opens the tab and exits", and you get a tab that never connects and no working
daemon — with the design's own mandate that the daemon be `setsid`-detached and never tty-parented
maximising the chance it outlives the Bash call that created it.

With a recorded `reachable` flag there is nothing to infer: bare `sideview` sees `reachable = 0`,
replaces that daemon instead of deferring to it, and says why. Comparing the recorded `netns` inode
against its own also tells any invocation *exactly* whether the row describes a daemon in its own
namespace, with no heuristic involved.

#### Belt and braces, and why over-eagerness is free

Refuse to auto-spawn if **any** of: only-`lo`; net-ns inode ≥ `4026531840` (the kernel's boundary
between initial and dynamically-created namespaces — real, but an internal detail not to lean on
alone); `/proc/1/comm` is `bwrap`; `uid_map` maps a single uid.

The asymmetry is what makes a conservative stack of signals the right call rather than sloppy: a
false positive costs one printed line — the fallback message we would print anyway — while a false
negative costs the failure above, which presents as inexplicable rendering and takes an afternoon to
diagnose. Given that trade, prefer refusing.

**Linux only.** None of `/proc`, namespaces or `bwrap` exists on macOS, where the sandbox is
Seatbelt and creates no network namespace. Elsewhere, assume reachable and let the daemon's recorded
flag be the authority.

### Knowing whether the daemon is actually alive

Harder than it looks, and worth getting right, because from inside the sandbox **every obvious
method is unavailable**: a direct `connect()` can't reach the port, and a pid check can't see a host
process through the PID namespace. Treat the store as the only channel. (It isn't *quite* — the
harness proxy can reach the host, per the section below — but that is Claude-Code-specific, needs
credentials from the environment, and must never be the thing this depends on.)

A heartbeat timestamp on its own isn't enough. It says the daemon was alive *N seconds ago*, so
right after a crash it still looks healthy; and if something else grabbed the port in the
meantime, the row now points at a stranger. So: a cheap hint, plus a definitive check when the
hint is doubted.

```sql
daemon(instance_id, pid, port, version, started_at, last_seen, ping, pong,
       netns, reachable)                                                     -- one row
```

**Fast path — the hint.** `last_seen`, refreshed every few seconds, read for free in the same
transaction that writes the block. Fresh means carry on and say nothing. This keeps the common
case inside the latency budget, since it costs no extra round trip.

**Doubt path — the proof.** When `last_seen` looks stale, or on an explicit `sideview status`, the
CLI bumps `ping` and waits up to ~500ms for `pong` to match. The daemon is already polling
`PRAGMA data_version` several times a second, so a live one answers in about the time it takes to
notice a new block. This is *definitive* rather than probabilistic, and it has a property a TCP
probe wouldn't even if we could make one: an unrelated process that inherited the port cannot
forge a `pong` in our database.

`instance_id` is regenerated at every start and carried through ping/pong, so an ack can never be
mistaken for one from a previous incarnation.

**Clean shutdown clears the row**; a crash leaves it, which is exactly what the timestamp and the
ping are for. Blocks written while nothing is listening are never lost — they render the moment a
daemon comes back.

**And the human has a better channel than the agent does.** The page holds an SSE connection, so
it *knows immediately* when the daemon dies — no polling, no window. Show a visible "disconnected,
reconnecting" banner and let `EventSource` do its own reconnection. You are the person who can
restart it, you're the one looking at the tab, and you learn faster than any CLI could tell you.
Agent-side detection is for reporting, not for alerting.

**Change detection is the daemon polling `PRAGMA data_version`** a few times a second. Cheap, no
inotify, no watcher edge cases, ~100ms of latency nobody perceives. (The HTTP notification idea
from an earlier draft is off again — it was unlocked by "we're unsandboxed anyway", and we no
longer are. Store and filesystem in both directions.)

**Run it in the foreground.** You started it, so the terminal is the natural home for its log and
Ctrl-C is the natural teardown — no pidfiles to reap, no `--stop` to remember. `--detach` exists
for anyone who wants it.

### Sessions are URLs, and one tab sees all of them

`/s/<session>` per session, and `/` is a live shell listing them that switches between them over
the same SSE stream — so you keep **one tab, indefinitely**, and new sessions appear in it rather
than stranding you on a dead URL. Default selection follows the most recently active session
unless you've deliberately clicked another; a header strip is enough UI for v0.

**The switcher lists recent sessions only.** Nothing is deleted — old sessions stay in the store
and stay reachable by URL — but the strip shows the recently active ones so it doesn't grow into a
wall. That's the whole of retention in v0: a display filter, not a garbage collector, which means
no decisions about what's safe to destroy and nothing to undo if the cutoff turns out wrong.

This is what makes per-project work at all, and it's the thing I'd missed when arguing for
per-session earlier. Without it, a new session means a new URL that only the agent knows, and the
agent has no reliable way to tell you.

**On who opens the browser:** you do, via bare `sideview`. A sandboxed agent can't be relied on to
launch one — `xdg-open` needs a desktop session the sandbox doesn't reach — so the CLI prints the
session's URL and leaves it there. It'll try to open when it can, but the tab you already have is
the normal path.

**And this kills the URL-delivery problem.** Earlier drafts worried that the CLI's output goes to
the agent rather than to you, so a URL could never reach a human. Now *you* start the daemon, so
you see the URL in your own terminal before any agent exists.

**Fallback when no daemon is running.** The CLI writes the block regardless — nothing is ever lost —
then exits 0 and prints one line: *"no daemon running — run `sideview` in /path/to/project to see
this."* Everything written so far renders the moment one starts.

Then **the skill tells the agent to offer to start it**, by re-running `sideview --detach` with the
sandbox disabled. That is one approval prompt, after which you never think about daemons again — and
it is the closest v0 gets to the README's no-ceremony bar under a sandbox. The printed line stays as
the fallback for other harnesses and for when you decline.

### Who can escalate, precisely

Three different questions get confused here, and the distinction is measured rather than assumed:

**The CLI process cannot escalate.** The sandbox is `bwrap --unshare-net --unshare-pid
--unshare-user --cap-drop ALL`, applied at exec by the harness; nothing inside undoes it, and a child
process has no channel through which to request anything. So the CLI itself never prompts, ever.

**The agent can, through the harness's permission gate** — by re-running the Bash call with the
sandbox disabled. Verified: a `setsid nohup`'d listener started that way binds a real host port,
**survives after the tool call returns**, and serves the host's browser. This is why the option
exists at all, and an earlier draft was wrong to record it as unimplementable: it isn't the CLI
asking, it's the agent asking, which is a mechanism that already exists.

**A daemon started inside the sandbox is still useless**, which is the constraint this whole document
is built on and it survives intact. Measured in both directions: a listener bound inside the
namespace does not appear on the host at all (`--unshare-net`), and the host cannot reach it. So the
escalation path is not an optimisation of agent-spawned daemons — it is the agent asking for a
*non-sandboxed* invocation, which is a different thing.

### The store is not quite the only channel, and that is worth knowing

An earlier draft asserted that from inside the sandbox every route to a host daemon is closed. Two of
three are: a raw TCP connect to the host's loopback is refused, and a pid check can't see through the
PID namespace. But **egress is a host-side proxy over a bind-mounted unix socket**, fronted by
in-namespace `socat` on `127.0.0.1:3128` (HTTP) and `:1080` (SOCKS), and it forwards to the host's
loopback perfectly well — verified with a listener on the host, 200, confirmed in its access log.

Three traps in testing it, all of which produced a wrong answer first time round: `$no_proxy` lists
`127.0.0.1`, so a client will silently bypass the proxy you think you're testing; the credentials are
in `$HTTP_PROXY` and regenerate per invocation, so nothing can be hardcoded; and
`$CLAUDE_CODE_HOST_HTTP_PROXY_PORT` names a *host* port that is refused from inside — the in-namespace
socat ports are the reachable ones.

**Keep the store as the mandatory path anyway.** It works under every harness, needs no credentials,
and the polling latency it costs is ~100ms that nobody perceives. What the proxy earns is an *optional*
liveness check: a real HTTP GET against the daemon is better evidence than any inference from the
store, so use it when it's available and never depend on it.

## Which session am I?

Load-bearing now that one daemon hosts many sessions: get this wrong and two concurrent agents
merge into one page. First match wins:

1. `--session <id>` — explicit, and the escape hatch for cron jobs and anything odd.
2. `$SIDEVIEW_SESSION` — for wrapping.
3. **`$CLAUDE_CODE_SESSION_ID`** — Claude Code sets this, re-verified inside a sandboxed Bash call
   on 2026-08-02 (`8f608544-…`, Claude Code 2.1.220). Stable across the many separate Bash
   invocations that make up one agent session, which is exactly the property needed.

   **Subagents share it.** `$CLAUDE_CODE_CHILD_SESSION=1` is set alongside the *same*
   `$CLAUDE_CODE_SESSION_ID`, so a subagent's blocks land in its parent's page. Take that as the
   decision rather than an accident: a subagent is doing the parent's work, and one page per fan-out
   would scatter a single task across a switcher full of near-identical entries. If it ever needs
   splitting, `$CLAUDE_CODE_CHILD_SESSION` is the hook to split on.
4. `$TMUX_PANE` or equivalent — for a human driving the CLI by hand.
5. The working directory, as a last resort.

Note what is *not* on that list: the controlling tty. Agent Bash calls have none (`tty` returns
"not a tty"), and each invocation is a fresh shell, so there is no persistent process to key on.
Without a harness-provided id the fallback would be cwd, and cwd collapses concurrent agents into
a single session — which is precisely the failure this ordering exists to avoid.

`$CLAUDECODE` and `$AI_AGENT` are also set, and are the cheap way to tell we're inside an agent at
all — useful for deciding whether to attempt a browser launch or just print the URL.

## Where the store lives

Walk up from the working directory for an existing `.sideview/`, like `.git`. If none is found,
create one in the nearest enclosing repository root; failing that, in the working directory
itself. Print the path the first time one is created, so nobody discovers a stray `.sideview/`
weeks later and wonders what made it.

**With one exception: a worktree resolves to the main checkout's store.** Ask git for
`--git-common-dir` and put the store beside *that*, not beside the worktree's own root. The naive
walk-up gives every worktree its own store, hence its own daemon, hence a hand-started daemon per
worktree — which quietly turns "one daemon per project, asked once ever" into a question you answer
every time you branch. Since worktree-per-task is the normal workflow here, that would have been the
common case rather than an edge one. DESIGN.md already required this and the walk-up rule
contradicted it.

Sessions are what separate concurrent work, and they do that whether or not the work is in the same
directory — so nothing is lost by sharing the store, and blocks written from a worktree stay
visible in the one tab you keep open.

## One daemon per project

Not per machine, not per session. It hosts one project's store and serves every session in it.

What this gives up versus per-session is worth naming honestly, since none of it turned out to be
decisive: single-window becomes bookkeeping rather than structure (though the daemon already
tracks live SSE viewers per session, so it's nearly free); one crash takes out every session's
page (mild, when state is in SQLite and a restart loses nothing); and a long-lived process can
fall behind an upgraded binary, which is why the version check below stays.

What it buys is that nobody has to think about daemons again after the first time.

### Nothing in the home directory

All state lives in `.sideview/` inside the project. Not `~/.local/state`, not `~/.cache`, not
`$XDG_RUNTIME_DIR` — the sandbox's write allowlist covers the working directory and not the home
directory, so anything under `$HOME` buys a second permission prompt for no benefit.

```
.sideview/
  sideview.db         # blocks, sessions, and the daemons table
  .gitignore          # contains "*" — the directory ignores itself
  blobs/
```

Daemon registration and liveness are rows rather than files, so the CLI answers "is it up?" with
the same query it uses for everything else. The daemon logs to its own terminal, since you started
it there.

The self-ignoring `.gitignore` is worth creating on first run: sideview should never make
`git status` dirty, and since version control was explicitly dropped as a goal, nothing here
wants committing. Export and pack are the paths out.

### Port: remembered, because now there's a tab worth keeping

Per-project changes the calculation. With one long-lived daemon and one tab you keep open for
days, a stable port is worth having — **`EventSource` reconnects to the same origin**, so a same
port means restarting the daemon and having your open window simply pick up again.

So: allocate dynamically on first run, record it in the store, reuse it on subsequent starts. If
it's taken, take another and print the new URL — you're looking at the terminal you started it
in, so that's a non-event rather than a mystery.

Bookmarks and `ssh -L` were the wrong justification for this earlier; SSE reconnection is the real
one, and under per-project it finally matters.

### Remote: tailnet by default when there is one

Remote is the *normal* case here — agent on the remote box, browser on the laptop, persistent herdr
session — so loopback-only would put a setup step in the common path, which is exactly the ceremony
the README swears off. So the default is **`--bind auto`: loopback, plus the tailnet address if a
tailnet exists.** No flag, no forwarding, no token.

```
$ sideview
  local:   http://127.0.0.1:41779
  tailnet: http://100.102.221.40:41779      (any tailnet node can read this)

$ sideview --bind loopback
  local:   http://127.0.0.1:41779
```

`--bind loopback` (or `SIDEVIEW_BIND=loopback`) opts out; there is no persistence for it in v0, since
bare `sideview` is typed by hand once per project anyway.

**Detection is free, so "if available" costs nothing.** Enumerating interfaces in-process measures
**29µs** on this machine — against a 50ms startup budget — and it happens once when the daemon binds,
not on any CLI call, so the per-block latency that actually matters is untouched. Nothing shells out
to the `tailscale` binary and nothing talks to `tailscaled`.

**Detect by address range, not by interface name.** Any address in `100.64.0.0/10` — Tailscale's
CGNAT range — is the marker; `tailscale0` is only the conventional name and is wrong under userspace
mode and on macOS (`utun*`). Measured here: `tailscale0` holds `100.102.221.40/32` and
`fd7a:115c:a1e0::436:dd29/128`, so the v6 ULA range is the same test in the other family and worth
binding too. The known false positive is that `100.64.0.0/10` is shared CGNAT space some ISPs use on
real WAN interfaces; it stays tolerable only because we bind *that one address* and never the
wildcard.

**Print the IP, not a guessed hostname.** An earlier draft printed `http://lenovo:41779`, which was an
assumption: this host's `hostname` is `cachyos-x8664`, and the MagicDNS name is a tailnet-side
property that can be renamed in the admin console independently of it. The real name needs
`tailscale status --json` — a subprocess plus a daemon roundtrip that can hang when `tailscaled` is
wedged — which has no business on the startup path. The IP always resolves from any tailnet node and
needs no DNS at all.

Four more things that shape this:

- **`0.0.0.0` remains the one clearly wrong answer.** This host has `wlan0` and `eno1`, so the
  wildcard would expose plans to the home LAN rather than just the tailnet.
- **Binding can fail, and must degrade rather than die.** `bind()` on an address that isn't up returns
  `EADDRNOTAVAIL`, so if `tailscaled` starts *after* sideview there is no tailnet address to bind:
  fall back to loopback-only and say so in the printed output. A tailnet that appears later needs a
  daemon restart, which costs nothing because all state is in SQLite. Watching for interface changes
  is not worth it in v0.
- **No token, deliberately, and this is where the decision now bites.** The default is a page every
  tailnet node can read, which is a real exposure rather than a theoretical one — accepted because a
  personal tailnet is a set of your own devices, and because the alternative costs the normal case a
  setup step. A `?t=…` secret would not help much anyway: the *agent* prints URLs, so the token would
  land in transcripts and shell history, which is a worse disclosure surface than the thing it
  protects. **The trigger to revisit is a tailnet with a node you don't control** — a colleague's
  shared device, a CI runner. At that point `--bind loopback` plus `tailscale serve` is the answer,
  and it is better than a token: HTTPS, real `Tailscale-User-Login` identity, no secret in the URL.
- **Verify that `tailscale serve` doesn't buffer SSE** before relying on that path. The whole product
  is one long-lived stream through what is, in that configuration, a reverse proxy.
  `X-Accel-Buffering: no` is already sent; whether Tailscale's proxy honours it is a fact to
  establish, not assume.

The stable remembered port is what makes all of these a one-time cost — direct tailnet access, a
`tailscale serve --bg`, an `ssh -L`, or a bookmark. An earlier draft argued the tailnet case on *N
ports cost the same as one*, which was a per-session-ports argument and is moot now that a project has
exactly one.

## What the daemon will serve

**Only paths inside the store's project root.** The `image` block points at a file and the daemon
serves it, which without a rule is path traversal via whatever an agent happens to write.
Resolve symlinks, compare against the root, refuse anything outside it, and return a clear error
rather than a 404 so a mistyped path is diagnosable.

**And therefore no idle exit.** Auto-exit was attractive as invisible infrastructure, but it
depends on being able to auto-restart, which is precisely what a sandboxed agent cannot do —
an idle exit would mean restarting by hand. Long-lived, no timeout. Simpler to build, too.

## The v0 schema

DESIGN.md's schema sketch predates the v0 cut — it has `plans`, `outputs`, `params` and provenance
tables, and no `daemon` row. This is the actual shape to create, and it is small enough to read in
one go:

```sql
PRAGMA journal_mode = WAL;   -- set once at creation; it persists

sessions(id TEXT PRIMARY KEY,          -- the resolved session id, see below
         label TEXT,                   -- human-facing, shown in the switcher
         cwd TEXT,
         detected_from TEXT,           -- which rung of the resolution chain matched
         next_block_seq INTEGER,       -- the counter behind `b7`
         started_at, last_active_at)

blocks  (id INTEGER PRIMARY KEY,       -- internal, monotonic
         session_id TEXT NOT NULL REFERENCES sessions(id),
         short_id TEXT NOT NULL,       -- `b7`, unique per session, what the agent sees
         ord TEXT NOT NULL,            -- lexicographic rank, so inserts never renumber
         type TEXT NOT NULL,           -- prose | markup | html | image
         version INTEGER NOT NULL,     -- spec version, per the don't-cut list
         spec_json TEXT NOT NULL,      -- reference, never content
         created_at, updated_at,
         UNIQUE(session_id, short_id))

daemon  (instance_id, pid, port, version, started_at, last_seen, ping, pong,
         netns, reachable)             -- one row
```

Four notes, each of which is load-bearing rather than decoration:

- **`short_id` is separate from `id`.** The agent-facing name is per-session and human-short; the
  primary key is neither. Conflating them is what makes the collision in the ids section unfixable.
- **`ord` is a rank string, not an integer.** v0 only ever appends, so any monotonic scheme works —
  but `update` is in scope and inserting between two blocks is the obvious next request, and
  renumbering neighbours is exactly the retrofit the don't-cut list warns about.
- **`session_id` is `NOT NULL`.** v0 has one surface, so there is no nullable `plan_id` to be
  mutually exclusive with yet. Promotion becomes an added column later, not a relaxed constraint.
- **No `outputs` table.** Nothing computes anything in v0; prose, markup, html and image are all
  spec-only. Adding it is additive when value blocks arrive.

## Schema migration

**`PRAGMA user_version` stepping, applied in-process on open.** Nobody should ever see
`sideview migrate`. [`rusqlite_migration`](https://crates.io/crates/rusqlite_migration) does
exactly this — an ordered list of `M::up()` steps keyed on `user_version` rather than a
metadata table, actively maintained, 3.6M downloads — and for a four-table schema a hand-rolled
`match` on `user_version` would also be fine. The choice that matters is `user_version` as the
marker, not the crate.

One `open_store()` used by both the CLI and the daemon, since they're the same binary. It opens,
takes `BEGIN IMMEDIATE`, migrates if needed, commits. Whoever arrives first migrates; the other
blocks briefly. Set `journal_mode=WAL` at creation — it persists, so it isn't a per-open step.

**Refuse to open a newer schema than you understand.** An old binary meeting a `user_version`
above its highest known migration must say so and stop, not proceed and corrupt.

**Copy the file before any non-additive migration.** `.sideview/liveplan-pre-N.db` or similar.
Trivial in a single binary and the difference between an annoyance and a lost plan.

**Prefer additive changes**, because SQLite's `ALTER TABLE` can add a column but not drop or
retype one. Anything structural needs the create-new / copy / drop / rename dance inside a
transaction, which is exactly the migration you want a backup for.

### The version-skew trap

This one is specific to having decided on a long-lived daemon with no idle exit: **you upgrade
the binary while the old daemon is still running.** The new CLI migrates the store forward, and
the old daemon is now reading a schema it doesn't know.

So the daemon records its version, and on mismatch the CLI prints one line — *"daemon is running
v0.3, this is v0.4; Ctrl-C it and run `sideview` again"* — and declines to migrate underneath it.
Same pattern as the daemon-not-reachable message, and the alternative is a class of bug that
presents as inexplicable rendering failures.

The message an earlier draft used — *restart it with `sideview daemon --restart`* — is dropped along
with the subcommand, because it doesn't survive contact with foreground ownership: the daemon is a
process in *your* terminal under Ctrl-C, so a CLI-issued restart would have to signal somebody
else's foreground job and then fail to bring it back, since the terminal that owned it has exited.
Telling the human to do the thing they were already positioned to do is both simpler and the only
version that works. The page's disconnected banner tells them at the same moment.

### Two versionings, not one

Keep these separate in your head, because conflating them causes trouble later:

- **`user_version`** — the shape of the tables. Handled here.
- **The per-block spec `version` + fallback** — whether *this renderer* understands *this block*.
  A snapshot opened a year later, or a block type newer than the page rendering it. That's the
  Adaptive Cards lesson from the don't-cut list, and it's an entirely different axis.

### Before the first tagged release

Migrations are churn while the schema is still moving. Until v0.1 ships to anyone, "delete
`.sideview/` and start again" is a legitimate strategy and saves real busywork. Start writing
proper migrations at the first release, and keep a `sideview reset` escape hatch afterwards.

## Transport: SSE, not websockets

SSE is enough for v0, and probably better than websockets well beyond it.

The traffic is almost entirely one-way — block added, block updated, output ready, log line
appended — and the browser has nothing to say back in v0 at all. Everything that arrives later
(a comment, a param change, a re-run request) is a plain `POST`, which is easier to debug with
`curl`, easier to log, and needs no message-type dispatch. Keeping the event channel and the
command channel separate is cleaner than multiplexing both over one socket.

Three concrete advantages, not just simplicity:

- **Reconnection is free and correct.** `EventSource` reconnects on its own and resends
  `Last-Event-ID`, so a laptop that slept for an hour reattaches and replays what it missed. A
  tab left open for days over a flaky tailnet is the expected usage, and with websockets that
  backoff-and-resume logic is ours to write and get wrong.
- **It passes through anything.** A plain long-lived GET needs no protocol upgrade, so
  `ssh -L` and `tailscale serve` are non-events.
- **Connection state is the viewer signal.** The one-window rule and idle-exit both need to
  know whether anyone is watching, and an open SSE stream answers that directly.

Two practical details: send `X-Accel-Buffering: no` so no reverse proxy buffers the stream, and
set a keep-alive interval so idle connections aren't reaped — `actix-web-lab`'s `sse` module
has keep-alive support built in, though it's off by default.

Websockets earn their place later for exactly one thing: **PTY blocks**, where bidirectional
low-latency keystrokes are the whole point. Proxying a *service block's* own websockets is a
separate concern again, and independent of how the daemon talks to its own page.

## Framework: actix-web

Use actix-web. Earlier drafts said `axum` as an unconsidered default, and there is nothing in
this design it does better — both are mature and fast, both serve files, both handle SSE, both
can reverse-proxy later for service blocks. For a solo project this size, familiarity dominates
every other consideration, and `actix-web-lab::sse` covers the one piece that matters.

## Small things, settled by default

None of these need thought; they're recorded so they don't get rediscovered as questions.

- **`markup` blocks are not sanitized.** Scripts run. This is a decision, not an oversight — the
  reasoning is in DESIGN.md's "Scripts in shared plans" and SHARING.md, not in this document, and
  it comes down to the block being code you own in a page only you can reach. It's written here
  because it is the first thing anyone reading the code will query.
- **Detached logging** goes to `.sideview/daemon.log`. In the foreground it goes to your terminal,
  which is the normal case.
- **`show` treats `.png .jpg .jpeg .gif .webp .svg` as images** and errors honestly on anything
  else, naming the type it didn't understand.

## Left deliberately unspecified

**Scroll behaviour when a block arrives.** The likely answer is to scroll only when already at the
bottom, so content follows you while watching but never yanks you away while reading above — but
this is a thing to feel rather than specify, and it wants a real page and a real streaming plan in
front of you. Decide it with your hands.

## Acknowledged, not re-opened

At this scope SQLite is a narrower win than it was — with only prose and HTML, files plus a
watcher would nearly do. Keep SQLite anyway, for precise patches and stable ids, and because
migrating onto it later is worse than starting on it. But it is no longer the obvious call it
was when tables and provenance were in scope.

## The spike that isn't v0

Service blocks are cut, but the premise risk shouldn't sit unexamined for months. Spend **one
afternoon, throwaway**: can a dev server be started, proxied, iframed into a page, and killed
cleanly? Not built properly — proven or disproven. If it turns out miserable, that reshapes the
roadmap while nothing depends on it yet.

## Done when

**Unsandboxed** — the real bar. From a machine with no daemon running, `sideview prose` then
`sideview markup` shows both, styled, in a browser window within a second, with no other
command typed. Three more invocations update the same window and open no new tabs.

**Sandboxed** — the daemon is already running, and a sandboxed agent's `sideview prose` reaches
the open window just as fast, through the filesystem alone. With the daemon *not* running, the
CLI says so and prints the one command that fixes it — and, per the detection rule, does **not**
spawn a daemon of its own.

**Sandboxed, nothing running, nothing typed by you** — the agent offers a sandbox-disabled
`sideview --detach`, you approve, and the page opens with every block written so far already on it.
This is the bar that matters for the no-ceremony aim, because it is the only path where you did
nothing in advance.

**The trap either bar can hide.** Run the unsandboxed test on a machine where an agent has already
tried the sandboxed one. If a namespaced daemon left a row behind, bare `sideview` must notice
`reachable = 0` and replace it rather than opening a tab at a port nothing is listening on. That
sequence is the regression test for the whole detection section, and it is the one a passing pair of
bars above would otherwise miss.
