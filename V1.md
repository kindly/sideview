# v1 — 0.1 on crates.io

v0 proved the mechanism: blocks stream from a sandboxed agent through the store to a live page,
and the page is worth looking at. v1 does two things. It **re-founds the tool on files** — the
canonical source of every page becomes a file in the project, never the database — and it makes
sideview a thing other people can install and other agents can drive. The release is still the
goal: everything in scope either closes a gap a stranger would hit in the first hour, or is
needed to publish honestly.

Scoped 2026-08-04, the day v0 closed at `4c639f4`; re-scoped the same evening, deliberately,
after the canonicality discussion recorded below. [V0.md](V0.md) remains the reference for
everything it specified; where this document contradicts it (the store as sole content home,
the `ord` column, block tombstones as the deletion story), this document wins.

**Process, set by the author at scoping: dogfood first.** Nothing in v1 is implemented before
its design has appeared on the live sideview page — sideview is the design channel for its own
v1. The plan page is the working artifact: kept terse (features and the goal; rationale lives
here), and revised through `update` rather than appended to.

## In

- **Pages are files** — the centerpiece; everything else lands on top of it.
- **Deleting sessions** — from the page and the CLI; now means deleting a file.
- **Harness independence** — proven live in codex, opencode and pi.
- **Code highlighting** — fenced code renders flat mono today; it should be highlighted.
- **Diff blocks** — `git diff | sideview diff`, rendered properly, navigable by file.
- **The release** — 0.1.0 on crates.io, with the vendored-asset licensing done right.

## Out (deferred, again deliberately)

- **Tables** (the querier/glide ambition) and **app subprocesses / whole-pane React blocks** —
  deferred explicitly by the author at scoping. The React ladder in [HANDOFF.md](HANDOFF.md)
  stays parked.
- **Service blocks, provenance, sharing** — unchanged from v0's Out list. (Note that `sv-diff`
  with a `src=` attribute would be the first service-shaped block; v1 ships the embedded-body
  form only.)
- **Committed to v2**, sketches recorded in the diff section: watched diffs (`src="git:…"` via
  gitoxide) and anchored comments (`sv-comment` blocks, content-based anchors that survive
  re-diffs, orphaning as "possibly resolved") — the latter refined twice on 2026-08-06, and
  the second pass (the author's) overrides the first (a sidecar feedback file, rejected the
  same day it was proposed). **Comments live in the db**, and the reason is a principle worth
  keeping: *the page file has one author; everything multi-writer goes through SQLite.* Files
  hold canon because a single agent writes each one; comments are multi-writer and bursty
  (the user tapping on mobile while the agent updates blocks), exactly the workload SQLite
  serializes and file-splicing merely survives. A `comments` table (session, target block id,
  text, created_at, seen_at) written by the daemon's comments-only endpoint — the page talks
  *about* the document, never *as* it — and rendered by folding each comment into the tail of
  its target block. **Orphans are a query, not a data state**: targets not among the file's
  current ids, computed at render time, shown in an orphans section at the page tail so
  feedback never silently vanishes; if the id returns, re-anchoring is automatic because
  nothing moved. The delete-the-db test keeps its honest reading: deleting the db loses
  *conversation*, never *documents*. **Annotations resolved 2026-08-07: both homes, split by
  intent** — the author was torn between file and db and the torn-ness was the answer, since
  the placement principle adjudicates each half. Plan-essential annotations are `sv-note`
  blocks in the file (one author, versioned, always visible); context notes are rows in the
  *same* comments table as user feedback, agent-written via `sideview comment` (the db half
  costs nothing — the schema doesn't care who authored). Visibility communicates status: seen
  without hovering means canon. Promotion bridges them, matching the system's lifecycle
  everywhere (throwaway pages promote by `mv`); and for diffs, the rule of thumb: annotations
  on moving content are conversation, on frozen content they may be canon. Per-line diff comments (2026-08-07): the churn risks
  rank wrong-reattach > visual jitter > loss, so anchors are fingerprints (line + two lines
  of context, path) resolved three-state per re-diff — exact follows silently, fuzzy follows
  wearing an "edited since commented" marker (context dominates for low-entropy lines like
  `}`; proximity breaks ties), below-confidence orphans rather than guesses. The backstop
  that makes the worst case acceptable: comments quote their anchor at creation, so placement
  is best-effort but meaning is permanent (GitHub's "outdated" precedent). Agents receive feedback via **`sideview watch
  [--timeout N]`**: a blocking read on the *store* (data_version polling — sandbox-compatible,
  no network, works regardless of who started the daemon) that prints comment events as they
  arrive or times out quietly, giving turn-based agents an "await the user's feedback" call;
  stderr nudges on ordinary commands are garnish, watch is the mechanism. **Placement is
  Sphinx's headerlink model** (author, 2026-08-06): the page reads as a clean document; hover
  a heading or paragraph and a small mark appears in the margin — click it to comment there.
  Existing comments obey the same law: invisible until their anchor is hovered, a faint
  count-dot on the mark the only tell. Anchoring below the block reuses the house identity
  rules — headings by their stable block-prefixed ids, paragraphs by content hash (normalized
  text, computed identically client- and daemon-side), so reordering follows comments and
  editing a commented paragraph orphans its comment into the query — arguably correct, since
  it no longer says what was commented on. Touch has no hover: mobile gets marks faintly
  visible and tap-to-reveal, a small design pass of its own when built.
- **v2, designed 2026-08-06 after a pi run broke the rail** (h-tags in a card row minted
  nonsense sections): **explicit agent-supplied outlines**, replacing inference for
  everything that isn't prose. The dividing principle, stated by the author and worth its
  weight: **sv files are canon — plans, version-control-worthy; the db holds what should not
  be versioned** (coordination, conversation, visual niceness). The outline is visual
  niceness, so the explicit form lives in the db: `sideview outline` reads an ordered list of
  entries (title + anchor, one level of nesting — ids and sub-ids) into an `outline` table
  per session; when present the rail uses it verbatim and inference is off. Prose derivation
  *stays* as the default because it is not inference — a `##` is document structure read
  from canon, zero drift, works in a fresh clone with an empty db. Markup and html inference
  is already gone (v1, same day): presentation headings are not sections. Anchors: markup
  authors put `id=` on their own elements; prose anchors are the comrak-derived
  `{block}-{slug}` ids; `--clear` returns to derivation.
- **v2-or-later, recorded 2026-08-06**: agent- and viewer-defined chip ordering — the standard
  precedence stack (creation order → an `order` key on `<sv-page>`, sparse like block ords,
  flowing through props untouched → drag-to-reorder remembered in localStorage). Decided
  against for v1: stable creation order may already dissolve the confusion that motivated it.
- Carried v0 items that don't gate 0.1: iframe autosizing, the mobile rail, the scroll-feel
  decision, `tailscale serve` SSE buffering, the framework question.

## Pages are files

### The dichotomy that forced this

Dogfooding v1's own plan exposed it on day one: the plan existed twice — as V1.md in the repo
and as blocks on the live page — and the author asked the question that unravels the v0
substrate: *which one is correct?* A plan that exists in two places is wrong in at least one of
them. When people write markdown or HTML plans, the artifact **is** the plan; v0's page was a
rendering of database rows that no git history covered, no PR could review, and no other agent
could `Read`.

Three resolutions were considered and the first two rejected:

- **Markdown-canonical** (a path-backed prose block rendering V1.md): rejected by the author —
  it caps the page at markdown forever and makes sideview "just an md renderer". The growth
  that makes the project interesting — diffs, tables, queries, service blocks — must be
  first-class in the canonical form, not squeezed through what markdown allows.
- **Export from the database**: doesn't dissolve the dichotomy, adds a generation step to it —
  the exported file is correct until the next `update`, then you're back to wondering.
- **The file is a block document** — chosen. Not a markdown file, not quite an HTML file: a
  sequence of typed blocks, the same block model the store already had, now living where
  documents belong.

This choice contradicts DESIGN.md's store-vs-interface section, which rejected "a markdown or
YAML spec" for four written-down reasons — and the answer to each is designed in, not
forgotten: stable block identity (the old objection was about unstructured text; `id=` gives a
block document addresses), precise patches (reparse-diff by id is not diff-and-guess; the
watcher firing mid-write is the named partial-write cost, tolerated rather than prevented),
transactional writes (a whole-file write lands a multi-block edit together; lost is protection
against non-atomic writers — the same named cost), and one-artifact (the db remains for
exactly the features that reason protected — outputs, history, feedback anchoring — attached
to ids now durable in a committed file). YAML specifically had a fifth, unwritten problem:
embedding prose means indentation-scoped block scalars, the same model-hostile shape as the
sphinx rejection, where raw-body tags need no escaping at all. The author's fair
counterpoint, recorded: a CLI-serialized YAML file read by a YAML parser is never
hand-fragile — nothing need be handwritten. True, but that reduces the file to machine
interchange; the requirement that won pages-are-files is *direct* editability — agents
string-editing, humans reviewing diffs, editors highlighting the embedded content — and it is
exactly under direct edits and diff review that block scalars are brittle and noisy. YAML
loses given that requirement, and the requirement is the feature. DESIGN.md carries the
superseded note.

An earlier incarnation of this project considered sphinx-style directives in markdown — blocks
with special powers inside a plain file, no database at all — and dismissed it because markdown
as the *host* was too basic for the pages wanted. The idea returns here with that objection
answered: nothing is the host. Prose and markup are peers; the directive set is the block-type
set, so every future block type (tables, queries) extends the file format for free. And the
very first attempt at this project was a folder called **fancyhtml** — v1 is that name growing
up: fancy HTML files, plus everything the first attempt lacked around them (the live page, the
sandbox-aware daemon, sessions, streaming).

### The sv-document

```html
<sv-page label="v1 — 0.1 on crates.io" outline="scrollspy">

<sv-prose id="intro">
## Deleting sessions
Plain markdown — tables, ```mermaid fences, even <div> examples — raw until the close tag.
</sv-prose>

<sv-markup id="metrics">
  <div class="row">…full Bootstrap, verbatim…</div>
</sv-markup>

<sv-diff id="schema">
…a unified diff, pasted or piped…
</sv-diff>

</sv-page>
```

The rules, few and uniform:

- The daemon parses this file — **never a browser's HTML parser** — so the format owns its own
  semantics. Block tags open at line start; a block's body is **raw bytes** until the matching
  close tag at line start. Nothing is entity-decoded, ever: a plain `<` inside a prose body is
  always right. This is what makes embedding non-HTML inside an HTML-flavoured file a
  non-problem; real HTML gives raw text only to `script`/`style`, but this isn't real HTML and
  doesn't pretend to be.
- Everything at top level is inside an `sv-` tag; one rule, no per-container exceptions.
- Tags are recognized at **column 0 only**. A body that needs to show literal sv-tags (this
  plan's own format examples — the edge surfaced on day one) indents them by a single space,
  the same move markdown makes with longer fences.
- `id=` attributes are recommended and stable; a block without one gets a content-hash identity
  (stable across moves; an edit reads as remove-and-add, which is acceptable).
- Page properties (`label`, `outline`) live on `<sv-page>` — authored presentation belongs in
  the canonical file, not in a database row.
- An unknown `sv-` tag renders as an honest "this sideview doesn't know `sv-table`" block — a
  newer file meeting an older binary degrades visibly, matching the spec-envelope philosophy
  from v0.
- Blocks don't nest, which buys recovery no stock parser can offer: a line-anchored `sv-`
  opener appearing inside a raw body almost certainly means the previous close tag was lost,
  so the scanner implicitly closes with a visible error and every later block stays healthy;
  an unclosed final block runs to end-of-file with the same visible note.
- Extension `.sv` — deliberately *not* `.sv.html` (author's call, 2026-08-05). A file that
  looks like HTML advertises HTML's contract, and tools that believe it do damage: formatters
  reflow raw bodies, editors auto-close tags mid-diff, models' escaping reflexes fire. Since
  no stock HTML parser can read this format correctly anyway (see the trail below), the
  costume bought nothing. The cost — plaintext rendering on GitHub, no default editor
  highlighting — is accepted.

On model ergonomics, considered explicitly (will LLMs be confused?): the shape — one file,
typed regions, a different language per region — is one of the most heavily-trained patterns
there is (Vue single-file components, MDX, markdown's own fences). The whole format is one
sentence to a model — *a page is `sv-` blocks; bodies are raw bytes until the closing tag
alone on its own line; never escape anything* — which was one of the author's acceptance
criteria. The one real risk is HTML-escaping reflexes firing inside a raw body; mitigated by
the never-decode rule (a model that ignores the instruction and writes plain `<` anyway is
still correct — the natural spelling always wins), by the skill carrying one canonical
example, and by the fact that most edits are string replacements inside a block that never
touch a delimiter.

### The format, stress-tested (2026-08-05)

The author probed this format from every direction before committing, over a full day of
design conversation; the alternatives and their one-line verdicts, so none is re-proposed
cold:

- **XML proper** (root element, stock parser): XML has no raw text — every body needs
  CDATA (its own `]]>` edge, escaping in a new costume), and parsing is all-or-nothing, so a
  torn mid-edit state fails the whole document instead of one block. The stock parser is the
  only thing XML wins, and it buys the wrong properties.
- **HTML-proper** ("any HTML parser can parse it"): true but useless — HTML5 hardwires raw
  text to `script`/`style`; a custom element's body gets entity-decoded and treeified, so
  markdown examples and diff lines are destroyed. Worst of all it *partially* works — simple
  bodies survive — which is a trap, not compatibility.
- **`<script type="text/sv-prose">` blocks**: the one genuinely stock-parseable form (script
  is raw-text; scraper parses it today). Killed by a core block type: `sv-html` bodies are
  whole documents that legitimately contain `</script>`, which terminates the enclosing
  script mid-line by HTML's rules, not ours. The fix is an escaping convention — the
  perpetual tax again.
- **Multipart/MIME-style boundaries**: it *is* a fence format, but with no stock win (real
  MIME demands CRLF and header discipline; hand-authored LF files mean a custom parser
  anyway), header boilerplate per block, and no editor affordances.
- **Per-block `---` frontmatter** (the SSG pattern repeated): frontmatter works because `---`
  is recognized once, at byte zero. Repeated, the delimiter must survive inside bodies — and
  `---` alone is a markdown horizontal rule, with `--- a/path` starting every file section of
  every diff. The precedent doesn't survive repetition.
- **YAML document streams**: `---`-separated streams are real YAML, but a stream is YAML all
  the way down — raw bodies would be block scalars, indentation-scoped, every line indented,
  torn by any column-0 line. Note the SSGs don't actually use YAML streaming: Jekyll and Hugo
  split the file with their own small splitter and hand only the header to YAML — the exact
  architecture chosen here.
- **JSON documents in a YAML stream** (valid — YAML 1.2 is a JSON superset, flow style needs
  no indentation): JSON strings can't hold literal newlines, so every body becomes one
  enormous escaped line — escaping errors in long prose, one-line diffs, unreviewable PRs.
  Machine interchange, not an authored artifact.
- **Markdown superset via comrak** (the serious runner-up, and nearly the winner): the page
  as a markdown file — ambient prose plus tilde-fenced `sv-*` blocks with YAML frontmatter
  and `{…}` attributes. Zero custom parser (comrak is already the prose renderer), raw
  bodies by CommonMark's own fence spec, GitHub renders plans in PRs, and the strongest
  semantic precedent there is (Jupyter's ecosystem fled JSON cells to jupytext — markdown
  with fenced, metadata-tagged cells). Declined by the author with reasons accepted here:
  markdown is a prose notation, not a data format — structure would ride on sourcepos
  slicing, fence-escalation rules and comrak's particulars; identity splits into two regimes
  (fenced blocks by id, ambient prose by hash); and the sv-tag files simply read better as a
  designed artifact. If the format ever needs a second life, this is the one to revisit.

On precedent, calibrated honestly: **Vue proves the mechanism, notebooks prove the
semantics.** Vue SFCs are parsed by Vue's own parser in a special mode ("top-level block
bodies are raw, sliced by offset") — proof that everyone with typed-region files writes their
own splitter, and that "stock parser" only ever means "custom parser maintained by someone
else" (markdown's fences included). But an SFC is a form with singleton slots — no order, no
ids, compiled as a unit. The semantic twin of an sv-document is a notebook: an ordered
sequence of typed, *identified* cells, live-patched by tooling — and nbformat added cell ids
for exactly the reason `id=` exists here.

### Two tiers of page, one bit of difference: who chose the path

- **Throwaway pages**: CLI authoring with no file in sight writes
  `.sideview/pages/<session-id>.sv`. The path is a pure function of the session id —
  findable without any registry — and `.sideview/`'s self-gitignore keeps it out of version
  control. This is v0's ephemeral behaviour, unchanged from the agent's point of view.
- **Document pages**: a `.sv` file created deliberately at a path in the repo, committed like
  any other doc.

Promotion is `mv` — a throwaway idea worth keeping moves into the repo, same format, same
rendering; a small `sideview session promote <dest>` can do the move and keep an open tab
following.

### The db, demoted to bookkeeping

The store keeps exactly what only it can do:

- **The daemon row** — liveness, supersession, the remembered port. Control state, not content.
- **Bindings** — session id → file path, plus last-active. A binding is the daemon's **watch
  list**: watching a handful of registered paths every 250ms is free; globbing a large repo
  four times a second is not. Bindings are created by authoring (throwaway tier) or by showing
  a file explicitly; a slow rescan at daemon startup rediscovers committed pages in a fresh
  clone. A registered file that's moved or deleted outside sideview renders an honest "file
  moved or deleted — was docs/plan.sv" page rather than vanishing.
- **Derived render/replay state** — whatever the daemon keeps to serve SSE replay efficiently.
  Rebuildable by rescanning files, by definition.

The test that keeps this honest: **delete the database and no content is lost** — only live
tabs' replay continuity and the daemon's bookkeeping, all of which regenerates. Casualties of
the demotion, all welcome: the `ord` column (order is file order), block tombstones and the
whole derived-rev-counter problem (replay state is derived, so nothing durable can regress),
and `export` as a feature (`cp`).

### The editing model

The CLI surface is unchanged: `sideview prose <<EOF` appends a block to the session's file
(assigning `b7`-style ids as before), `update b7` rewrites that block's region, both under a
per-file lock. Agents may equally edit the file directly — string edits are what agents are
best at, and better than re-piping whole blocks through heredocs. Either way the daemon
reparses on change, diffs against the previous block set by id, and emits surgical upserts for
only what changed — the live-patch property survives intact.

Two engineering costs, named rather than discovered later: **concurrent writers** (subagents
share a session id; the per-file lock is where SQLite transactions used to be), and **partial
writes** (not every agent write tool is atomic; a half-written file renders an honest parse
error that heals on the next mtime tick).

Migration: the existing store's sessions are serialized out to `.sideview/pages/` files and the
schema reshaped — a real migration with the pre-migration backup, even pre-release, because the
author's live store carries this plan.

## Deleting sessions

Deleting a page is deleting its file (and its binding). From the page: an ✕ on the session
chip, two-step (first click arms, second confirms, disarms on its own) — still the browser's
first write into the store, tidying power rather than authoring power, proportionate to a page
already trusted to read everything. From the CLI: `sideview session rm [id]`, no id meaning
your own, matching `session set`; deletion never auto-spawns a daemon. Clients learn about
absence from the sessions snapshot they already receive on every connection and change.

For the record, three designs preceded this and each fell to a simpler one: a
`deleted_sessions(id, rev)` table (extra table, mental join); `deleted_at`/`removed_rev`
columns with removal events merged into replay (machinery to tell clients what the snapshot
already says); hard `DELETE` with the rev counter moved to `meta` (right about the counter
being the *only* v0 obstacle — then the substrate change made even that moot). The lesson the
author drew, worth keeping: v0 couldn't delete because its counter was derived from the rows;
make replay state derived from durable content — not the reverse — and deletion stops being
dangerous at all.

## More harnesses than one

The premise ("a visual side channel for CLI agents") never said Claude. Three couplings say it
today.

### Skills converged — installation is just paths now

Every target harness speaks the SKILL.md format natively, so there is no porting problem, only
an installation matrix:

| harness | user-level skills dir | notes |
|---|---|---|
| Claude Code | `~/.claude/skills/` | v0's only target |
| codex | `~/.codex/skills/` | also reads the cross-agent `~/.agents/skills/` |
| opencode | `~/.config/opencode/skills/` | *also reads `~/.claude/skills/` and `~/.agents/skills/`* |
| pi | `~/.pi/agent/skills/` | recursive discovery |

`sideview skill install` grows from one hardcoded path to: detect which harnesses exist (by
their config dirs), install to each, report each. `--agent claude|codex|opencode|pi` scopes it.
`sideview status`'s drift line reports per harness. The "deliberate exception to nothing-in-HOME"
rationale in `skill.rs` is unchanged — run once, by the user, unsandboxed.

Rejected: installing only to `~/.agents/skills/` and calling it the standard. Claude Code
doesn't read it, and "install once, works nowhere you actually work" is the wrong kind of neat.

### Session identity

Answered empirically by the matrix (2026-08-06), correcting the research: **codex 0.146
exposes no session identifier to shell tools** (`CODEX_THREAD_ID` appears in its MCP surface,
not its shell env — the rung stays as cheap insurance for later versions); **opencode sets
`OPENCODE_PID`**, its server process — instance-grade identity, tmux-pane calibre, now a rung
(`opencode:<pid>`); **pi sets only markers** (`PI_CODING_AGENT=true`, model/provider vars, no
id) and lands on the cwd rung. Consequence, observed live: two env-less harnesses in the same
project share the cwd session — pi's `--label` overwrote codex's page label mid-matrix. The
chain's shape and precedence are unchanged; the fallback is working, coarse identity, exactly
as designed. (The matrix also found `--session ''` minting an empty-id session — a codex model
invented the flag spelling; empty explicit ids now fall through the chain.)

### The sandbox model is Claude's — the others may be easier

v0's central constraint (each sandboxed Bash gets its own network namespace, so a spawned
daemon is unreachable) is specifically Claude Code's sandbox. codex on Linux uses
landlock+seccomp — no network namespace — so a daemon spawned under codex may be plainly
reachable, in which case auto-spawn *just works* there and the netcheck verdict should say so.
Or bind may fail outright, which the existing spawn path already reports honestly. This is not
designable from the armchair: the deliverable is a tested matrix (harness × spawn attempt ×
verdict × page reachable), and whatever netcheck adjustments the matrix demands. The skill
prose also drops its Claude-isms ("one approval", sandbox phrasing) in favour of words any
harness's user recognises.

### Done when (harness leg)

Each of codex, opencode and pi, installed and pointed at a scratch project, can: activate the
skill, write blocks that appear on a live page, get a distinct session per harness session, and
either start the daemon or receive the honest instruction that the human must. Recorded in
HANDOFF with the same specificity as the v0 experiments.

## Code highlighting

Server-side, at render time, with syntect — comrak already renders prose and has a syntect
adapter behind a feature flag, so highlighting is the same pass that builds the HTML, not a
second system. Class-based output (never inline styles), because the page has two themes and
one rendered HTML string must serve both. The classes get a hand-tuned theme in `sideview.css`,
light and dark, in the print-duotone spirit — ink for the load-bearing tokens, muted greys for
punctuation and comments, nothing rainbow. Bootstrap's own `pre`/`code` treatment stays as the
frame.

Rejected: highlight.js vendored client-side — a third vendored JS payload, a visible re-paint
after every SSE patch, and highlighting drifting out of the render path that owns everything
else. Rejected: syntect's inline-style themes — pick one and the other theme gets the wrong
colors baked in.

Use the pure-Rust regex backend (`default-fancy`), not the C oniguruma dependency; check what
the syntax-set embed does to binary size and note it in HANDOFF.

## Diff blocks

```bash
git diff | sideview diff          # or: git show <sha> | sideview diff
```

`sv-diff`, the fourth block type in the file format, holding unified diff text raw in its body.
Piping is the point: the diff flows from git to the page without ever entering the model's
context — the same property reference-never-embed protects, achieved by the shell rather than
by a path. (An agent that already has a diff in hand may heredoc it; nothing checks provenance.)

Rendering is server-side like everything else, and ships **both unified and side-by-side**
views (author's call, 2026-08-05, after a survey of the JS and Rust ecosystems). The stack:

- **`diffy`** parses the patch (git's extended format included) into files, hunks and lines.
  It parses all-or-nothing, and the block contract is per-file tolerance where garbage degrades
  to plain mono (`render::block()` never errors) — if real `git diff` output ever trips it, the
  replacement is a small tolerant hand parser for the split; the parser was never the hard part.
- **The aligned model is ours**: within a hunk, runs of removed/added lines pair index-wise,
  unpaired lines spill against empty cells. Both views render from this one model — unified
  interleaves it, side-by-side is the two-column reading of it.
- **`similar`** (dependency-free, pure Rust — same spirit as the syntect `default-fancy`
  choice) marks word-level `<del>`/`<ins>` spans within each paired line, gated by its
  similarity ratio so emphasis stays signal rather than noise on unrelated pairs.
- File headers become sections, hunks become line-numbered runs, `+`/`−` lines get tinted
  duotone backgrounds; each file's path becomes an outline heading, so the contents rail
  navigates a multi-file diff for free — this is the feature, not a flourish.

The view choice reuses the outline rail's symmetry: `view="split|unified"` on `<sv-diff>` is
the agent's default, a small client toggle is the viewer's override. Both views live in the
block's HTML with the inactive one hidden, so toggling is instant; that doubles the payload
per diff block — fine at plan scale, and a re-render endpoint is the escape hatch if huge
diffs ever hurt. Side-by-side takes the full-width breakout column and collapses to unified
on narrow screens.

Rejected: **diff2html** (MIT, ~100 KB minified, genuinely good — both views, sync scroll,
line-matching). It would have been faster to ship, but the outline contract forces a Rust
parse of every patch anyway (headings are derived server-side at event time), so a JS renderer
means two parsers of the same patch drifting on weird diffs; it re-admits exactly what the
highlighting decision rejected (a client-side re-paint outside the render path, without
mermaid's only-exists-in-the-browser excuse); and its GitHub-look stylesheet would be fought,
not used. Framework diff components (git-diff-view, react-diff-view) were out on arrival —
no framework on the page, and none arrives via a block type.

Deferred within diff: syntax highlighting inside diff lines. **Watched diffs are committed to
v2** (author, 2026-08-05): `src="git:…"` on `sv-diff`, re-diffed by the daemon on its poll
tick, so a page can hold a live view of the working tree. The mechanism is settled now so v2
inherits a decision rather than a question: **gitoxide (`gix`), never a `git` subprocess**.
`git diff` honors external diff drivers and textconv filters from `.gitattributes` + repo
config — both writable by a sandboxed agent — so shelling out turns page content into
host-side code execution even with a perfectly sanitized argv; a library has no such
machinery, and the class is absent by construction rather than disabled by discipline. What
remains for v2 is a constrained `git:` revspec grammar (validating data, not sanitizing an
argv) and checking gix's working-tree-diff and rename-detection maturity at build time.
Meanwhile the v1 form is a snapshot: an agent that wants the page to track progress re-pipes
through `update`. Judge the rest on real diffs.

**Also committed to v2 (author, 2026-08-05): anchored comments.** (Watched diffs were
re-sequenced out of v2 on 2026-08-07 — the author needed possibility proven, not the feature
built; the settled mechanism above waits intact for a later version.) The design sketch, so it
doesn't evaporate: comments are blocks in the file — `<sv-comment target="b7"
line="src/store.rs:42" side="new">` — which inherits everything (versioned with the page,
CLI- or edit-authored, reviewed in PRs beside what they annotate); the renderer folds them
into the target block's HTML at render time, so the reparse-diff patches exactly one block
per comment change with no new machinery. Anchors into *snapshot* diffs are frozen content —
trivial. Anchors into **watched** diffs must be content-based, not positional: record the
anchored line's text plus a context fingerprint at comment time, re-resolve on every re-diff
(`similar` is already in the tree for fuzzy matching), and degrade honestly — line moved →
follows; line edited beyond recognition → file-level orphan; file left the diff →
block-level orphan. The orphan state is semantically load-bearing, not a failure: on a
watched diff a comment's anchor disappearing usually means *the feedback was addressed* —
render it as "possibly resolved" (GitHub's "outdated" label is the precedent). Note that
this pairing was a founding motivation: DESIGN.md's case for stable block identity was
"feedback anchors to a block and has to survive rewriting." One decision deliberately left
open: comments *from the browser* hand content-authorship to anyone who can see the page —
a trust-model expansion to make on purpose (the ✕ was tidying power; this is authoring
power), not a byproduct of shipping the block type.

## Releasing 0.1.0

- **The substrate lands before the release**: 0.1's file format is the real one, not a format
  shipped knowing its replacement.
- **Crate metadata**: description, `license`, `readme`, `repository`, keywords. License and
  repository URL are the author's call (MIT is the working default until confirmed).
- **Vendored assets ship inside the crate** (rust-embed), so their licenses ship too: a
  `THIRD-PARTY.md` covering Bootstrap (MIT), mermaid (MIT), IBM Plex (OFL — text already
  vendored). All are permissive and redistribution-clean; the work is the notice, not the law.
- **Size**: mermaid.min.js is 3.5 MB; the whole package lands well under crates.io's 10 MB
  cap. Verify with `cargo package --list` and note the number.
- **`cargo publish --dry-run`** must pass from a clean checkout. The actual publish needs the
  author's crates.io token and is theirs to run (or to hand over deliberately).
- Migration discipline flips at this release: every schema change after 0.1.0 is a real
  migration. (The substrate migration before it runs as a real one too — the author's store
  carries live content.)

## Done when

1. Every page is a file: CLI authoring writes it, editing a registered repo page patches the
   open tab within a tick, and deleting the database loses no content (test-pinned where
   feasible).
2. A broken or half-written file renders an honest parse-error block that heals on the next
   save; an unknown `sv-` tag degrades visibly, not silently.
3. A session can be deleted from the page (two-step ✕) and from the CLI — by deleting its
   file; a reconnecting client converges.
4. Fenced code in prose is highlighted, correctly in both themes, with no client-side JS.
5. A multi-file `git diff` piped through `sideview diff` renders with per-file outline
   navigation and honest fallback on garbage input.
6. The harness matrix (Claude Code, codex, opencode, pi) is tested live and recorded; skill
   install reaches all four; session identity is distinct in each.
7. `cargo publish --dry-run` passes; metadata and third-party notices are complete; 0.1.0 is
   published (author's token) or ready-to-publish awaiting only that.
